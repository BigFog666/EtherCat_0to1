# 从 PC 的目标位置，一直追到板端和返回帧

先记住硬件职责：PC 上的 SOEM 是主站；LAN9252 是从站控制器 ESC，负责以太网 EtherCAT 帧的硬件处理、寄存器和过程 RAM；STM32 通过 SPI 读写 ESC，运行 SSC 和关节应用。STM32 自带的 Ethernet MAC 不参与本项目 EtherCAT 链路。电机模型在 MCU 中，没有外接驱动器或电机。

```mermaid
flowchart LR
  M[PC / SOEM 主站] -->|EtherCAT 二层帧| E[LAN9252 / ESC]
  E -->|SPI PDI / RxPDO| S[STM32 / SSC]
  S -->|完整命令快照| J[关节模型与 CiA402 状态]
  J -->|完整反馈快照| S
  S -->|SPI PDI / TxPDO| E
  E -->|返回 EtherCAT 帧| M
```

## 1. 主站先配置，随后才周期交换

主站入口在 `master/joint_master.c`。

1. `ecx_init` 打开指定 Npcap 网卡。`List` 只枚举网卡，既不发现从站也不证明真实收发。
2. `ecx_config_init` 发现从站，读取 EEPROM/SII、分配站地址、设置 Mailbox 等，并请求 PREOP。Scan 只走发现过程，退出时请求 INIT。
3. `ecx_statecheck` 等待 PREOP，随后 `ecx_readstate` 刷新实际从站的状态缓存，再执行 `check_dictionary`，用 SDO Upload 读 1018 身份、1C12/1C13 分配、1600/1A00 映射和 6502 支持模式。主站采用固定映射，不改写这些配置。本次实测修复了一个缓存问题：SOEM 2 的 `ecx_statecheck(..., 0, ...)` 只更新虚拟聚合站 0，Mailbox 发送却检查实际站 1；未刷新会在板子已到 PREOP 时仍拒绝发送 SDO。
4. `ecx_config_map_group` 建立 PC 的 IOmap，将从站字节映射到主站过程映像。该 API 会配置 SM/FMMU；不是简单分配 C 数组。
5. 等待 SAFEOP，先发送有效但禁止接通的 PDO，然后请求 OP 并持续交换，核对状态与预期 WKC。
6. OP 后每周期编码控制字/目标/模式、发送过程数据、接收返回帧、检查 WKC、解码反馈，再决定下周期命令。

Mailbox/SDO 是按索引访问参数的事务；PDO 是约定布局的周期数据。普通 EtherCAT 通信无需 TCP/UDP/IP。这里没有应用层 Socket 请求-回应服务；主站发起帧，ESC 在经过时处理数据，帧再返回主站。

| EtherCAT 状态 | 本项目关心什么 |
|---|---|
| INIT | 初始化，无普通 Mailbox/PDO 通信 |
| PREOP | Mailbox/SDO 可用，准备对象和映射 |
| SAFEOP | 输入过程数据可更新，应用输出保持安全处理 |
| OP | 允许应用处理有效输出 PDO；仍不等于 CiA402 已使能 |

状态区分根据 [Beckhoff EtherCAT 状态机说明](https://infosys.beckhoff.com/content/1033/el15xx/1036980875.html)。

## 2. 两个状态机分别管什么

EtherCAT 状态机决定“通信配置是否成立、应用能否使用主站输出”，例如 INIT→PREOP→SAFEOP→OP。CiA402 状态机决定“关节处于禁止、准备、接通、使能、停止还是故障”。OP 且 CiA402 禁止，是正常组合。

主站使用真实反馈推进使能：控制字 6，等待状态字掩码后 0x21；控制字 7，等待 0x23；控制字 15，等待 0x27。比较 `(statusword & 0x006F)`，因为状态字还有其他标志，例如本模型到达目标后为 `0x0427`，仍属于 Operation Enabled。

本模型接收到 cw=15 时，若尚在禁止状态，不直接跨过全部使能步骤。快速停止 cw=2 在模型中立即令速度归零，经过 Quick Stop 状态后回禁止；这不是物理驱动的减速斜坡或功能安全停止。Fault Reaction 也在主循环中很快经过，因此 PC 可能只采到最终 Fault，GDB/单元测试能观察中间状态。

## 3. PDO 的 12 个字节怎样对应

Rx/Tx 从**从站**看：RxPDO 是从站接收命令，TxPDO 是从站发送反馈。SOEM 的 outputs/inputs 从**主站**看：outputs 对应从站 RxPDO，inputs 对应从站 TxPDO。

| 字节偏移 | 主站输出 / 从站 RxPDO 1600 | 主站输入 / 从站 TxPDO 1A00 | 编码 |
|---|---|---|---|
| 0–1 | 6040 控制字 | 6041 状态字 | uint16，小端 |
| 2–5 | 607A 目标位置 | 6064 实际位置 | int32，小端 |
| 6–9 | 60FF 目标速度 | 606C 实际速度 | int32，小端 |
| 10 | 6060 模式请求 | 6061 模式显示 | int8 |
| 11 | 对齐填充 | 对齐填充 | 固定 0 |

本项目这组 PDO 是 12 字节，不沿用软件第十二课的 13 字节教学布局。编码在 `common/pdo.c`，逐字节处理，避免把未对齐网络指针直接转成 C 结构体；负数按 32 位补码编码。比如 cw=15、目标=-1000、速度=0、mode=8，命令为：

```text
0F 00 18 FC FF FF 00 00 00 00 08 00
```

配置对应：ESI 声明顺序/位长；SII 声明身份、Mailbox/SM；SSC 应用字典 1C12→1600、1C13→1A00；主站通过 SDO 对每条映射逐项检查；实际代码按相同偏移编码。任何一处改了都要重新对齐。

这块板保留了出厂 SII，身份、SPI 与 Mailbox 参数与本项目配套，但其中旧 IO 的 PDO/SM 长度描述仍为 1 字节。本版 SOEM 通过 CoE 从当前固件读取 PDO 映射，建立实际 12/12 字节 SM/FMMU；已通过真实通信验证。不要把这一结果理解为出厂 SII 与项目 ESI 每个字段都相同，或已经完成 TwinCAT 导入验收。

## 4. 一次目标 +1000 在板端经过哪些函数

`firmware/generated/cia402appl.c` 的 main：`HW_Init → Project_Init → MainInit → CiA402_Init → APPL_GenerateMapping → MainLoop + Project_Poll`。

主站输出到达 LAN9252 的 SM2 后，PDI IRQ/SSC 路径调用 `APPL_OutputMapping`，继而进入 `Project_OutputMapping`，解码 12 字节，保存命令、TIM5 接收时间和 generation。IRQ 不运行关节模型。

主循环的 `Project_Poll` 取得完整快照。如果 generation 改变，就调用 `joint_receive`；相同目标值仍是一帧新接收事件，会刷新时间。然后用 TIM5 当前计数和 `bEcatOutputUpdateRunning` 更新模型。当输出许可有效、CiA402 已使能、模式=8、没有超时或故障时，位置以最多 20000 计数/秒趋向目标，防止越过目标。比如从 0 到 1000，模型运动所需时间约 50ms；PC 实测还受命令到达、采样与调度影响。

模型结果发布为完整反馈快照，同时更新轴对象字典的状态、位置、速度、模式和错误码。SSC 的 `APPL_InputMapping → Project_InputMapping` 将快照编码到 SM3；返回帧带回主站，主站下一周期看到新反馈。它存在反馈延迟，主站不能假设同一周期已执行自己刚发的命令。

SDO Upload 可读取这些字典值。该应用的控制权在 PDO；SDO Download 到目标变量不会成为持续运动指令，随后会被模型/PDO 状态刷新。本版真实主站演示采用 SDO 读配置/诊断与 PDO 写命令，不宣称完成所有 SDO 写入服务的专项验收。

## 5. WKC 和时间要怎样理解

WKC 表示数据报按预期读写处理的工作计数，不等于设备数量。本项目从 SOEM 映射结果计算 `outputsWKC*2 + inputsWKC`，检查实际返回值严格相等。WKC 不符时，把该样本标为无效并结束演示，不能继续把上一周期的 input 字节当作当前真实状态。

WKC 正确也不代表 CiA402 状态正确。主站同时检查状态反馈和每个演示阶段的实际结果；意外故障会结束演示，只有由演示主动注入的故障才走计划内复位。

CSV 的 `interval_us` 是 PC 实际发送调用间隔，`roundtrip_us` 是 send/receive 调用耗时，`elapsed_us` 是 PC 时间，phase 是控制序列阶段。首行 interval=0 不参与周期统计。循环先写到内存，退到 SAFEOP 后才写 CSV，减少文件 IO 对周期的影响；Windows 调度仍会产生抖动。

## 6. 超时和复位为什么这么处理

应用阈值 `JOINT_TIMEOUT_US=100000`。最后有效 PDO 到当前时间达到阈值，就停止模型、锁存 FF04。SSC/ESC 的看门狗可以独立让通信退状态；应用模型始终由主循环维护，通信退到 SAFEOP/INIT 时不能继续旧运动。

普通断线期间主站无法收到板端状态，所以板端停止证据需来自独立调试观察或恢复后的 SDO。恢复 OP 和原因消失都不自动清除 Fault：还要新的 bit7 上升沿。否则恢复通信会无意重启旧动作。

本次已观察到主站退出后的 FF04 锁存、模型速度归零，并验证在同一 OP 会话中显式复位后完成演示。独立 `Reset` 会话退出后又停止 PDO，可能再次超时；重跑时用 `Demo -ResetBeforeDemo` 明确要求启动复位。物理拔线与 100ms 阈值的精确测量仍待另做实验。

| 错误码 | 本项目含义 |
|---|---|
| FF01 | 控制字 bit15 自定义注入 |
| FF02 | 模式不是 CSP=8 或 CSV=9 |
| FF03 | CSV 速度命令超出 ±20000 |
| FF04 | 有效输出 PDO 超时 |
| 8611 | 本模型位置命令/积分超过 ±100000 |

这些是本项目的简化行为。CSP 不是实物伺服位置闭环，CSV 没有电机速度环；错误码、选项码与全部 CiA402 状态转移尚未做产品级兼容性测试。

## 7. 阅读与修改练习

先读 `joint.h/c → pdo.h/c → ssc_bridge.c → demo_sequence.c → joint_master.c`，最后带着调用点读 SSC/驱动。

练习一：把最高速度从 20000 改为 10000，预测 +1000 到达时间由约 50ms 变为 100ms，再对照真实日志。练习二：目标值连续不变时，解释为什么 receive_count 增加而超时不发生。练习三：用旧故障原因保持有效的 bit7 请求，验证不能复位；原因消失后如果 bit7 一直为 1，仍要先降为 0 再升为 1。练习四：解释 WKC 正确但 sw=0x40 为什么不是通信故障。

原理参考：[LAN9252 官方数据手册](https://ww1.microchip.com/downloads/aemDocuments/documents/OTH/ProductDocuments/DataSheets/00001909A.pdf)；具体 SOEM 调用以固定版本的 `samples/simple_ng/simple_ng.c` 和 `include/soem/` 为准。
